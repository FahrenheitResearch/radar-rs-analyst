# Radar Workstation — Definitive Review, 2026-08-18

**Baseline:** `2101a0d` on `feat/m2-retained-map-scene` · Rust workspace, edition 2024 · reviewed read-only.
**Method:** five dimensions (seam-bugs, performance, smoothness, mobile, cap-scars), every finding adversarially verified against the code and re-measured on real Level II data (KDMX 2026-08-18 08:34Z, KTLX 2026-08-17 07:24Z, live cache + BowEcho cache on this machine). **51 findings confirmed, 2 refuted**, deduplicated here to ~45 distinct issues. Files owned by the four concurrent fix-workflows (globe, 3D opacity, view-stability, smooth-tables) were excluded from content findings; overlaps are flagged where a fix here touches their territory.

---

## 1. Executive summary

The engine is better than the experience. Under the hood this is a serious app — a disciplined generation-stamp render architecture, a measured quality ladder, bounded tile caching, a real test culture — but what a user sees today is a desktop-tethered viewer that blanks its panes to bare basemap on every frame, product, and tilt change; shows drag-start pixels for entire gestures while discarding 100% of the renders it computes during them; can freeze playback forever (and hot-loop the render worker) on one failed render; forgets every user choice on exit; and is effectively untouchable on glass — site taps dead, pinch dead in 3D, the whole information layer hover-gated. None of it is architecturally deep: the stamp/clock machinery makes almost every fix S or M, and the dominant failure mode is the app's own documented recurring pattern — both halves of a seam correct, the seam never joined. The 2D pane's own gesture reader, its own keep-texture comments, and its own cancel pattern already contain the fixes the other panes never received. The revoked 2000-line cap did real damage (a 1,999-line camera module shipped dead; the toolbar scattered across three files) but the scars are enumerable and cheap to heal.

**Top 5 actions by value:**

1. **Hold the last frame everywhere** (§2.1–2.3, all S): stop blanking panes, accept view-stale renders during gestures, break the failed-render freeze/livelock. This alone moves the app from prototype-feel to shipping-radar-app-feel.
2. **Do the touch input pass** (§3A): site tap via `interact_pointer_pos`, long-press = nearest S-band, pinch zoom in 3D, pinch centroid. Without these the iOS/Android app does not function.
3. **Lay the mobile substrate** (§3B): per-OS cache roots (live feed is dead on Android *today*), cache eviction (17.5 GB proven endpoint on this box), a mobile memory profile (defaults sum past jetsam), real persistence.
4. **Cache in the render worker** (§2.4, §4.2): derived fields recomputed 15–23 ms up to ~40×/s, moment caches rebuilt every request — the biggest desktop perf and mobile battery win.
5. **Wire or delete the dead camera module and unify 3D zoom input** (§2.7–2.8): Ctrl+scroll and trackpad pinch are dead in the 3D pane on desktop *today*, and the dead-notch zoom defect is already fixed in 1,999 lines of code nobody runs.

## 2. Fix now

Confirmed high-severity, ordered by value. Coordination note: §2.3 borders the in-flight view-stability workflow (`analyst_runtime/src/workspace.rs`) — sync before starting it.

### 2.1 Panes blank to bare basemap on every frame change, scrub notch, playback step, product switch, and tilt step
**high · S · files:** `crates/workstation_app/src/app.rs:1479` (`clear_all_panes`), `app.rs:1468` (`invalidate_semantic_panes`)

Both paths set `texture = None`, and `draw_pane` then paints chrome+map only (`pane_canvas.rs:232-234`). Callers: `advance_playback` (app.rs:731-737, 700 ms steps per `PLAYBACK_FRAME_TIME` app.rs:53), `commit_history_selection` on **every scrub notch** and go-live (app.rs:1553-1560; the slider emits `choose_frame` per notch, app.rs:1240-1246), `install_loaded_volume` on frame-signature change (app.rs:610-614) — and `current_frame_signature` includes `FrameStage` (app.rs:1532-1536), so **Preview→Partial→Complete promotions of the same live volume also blank**. The semantic path blanks on product change (app.rs:1000-1003), tilt step (app.rs:1755-1758), and initial product (app.rs:332); key-repeat tilt stepping keeps the pane blank most of the time. Replacement renders measured 1.6–29.2 ms per pane at 900 px on real KDMX, serialized across panes on the single render worker (`render_service.rs:107-125`) — up to ~160 ms of blank across four panes. The codebase already knows better in two adjacent places: the grown-volume branch keeps its texture with a comment saying clearing "would blink the pane to empty on every chunk" (app.rs:614-624), and the view path `invalidate_view_panes` (app.rs:1461-1466) deliberately keeps the on-screen texture (comment at app.rs:981-985).

**Related, folded in:** one failed live-chunk decode blanks every pane even though the on-screen frame is intact — the `Failed` arm calls `clear_all_panes` (app.rs:561-570) while history is untouched and the picture rebuilds ~100–300 ms later; the app's own philosophy 120 lines earlier rejects this ("blanking the map on one bad round trip would be a worse lie", app.rs:443-447).

**Fix:** split `clear_all_panes` into reset-state (pending_stamp, sweep via `reset_sweep` app.rs:1479-1489, status) and drop-texture. Hold the installed texture on frame/product/tilt changes until `install_render` swaps it (in-place update already exists, app.rs:672-684); playback pacing is preserved because `visible_panes_ready` (app.rs:1868-1877) compares stamps, so a stale texture still reads not-ready. Reserve the texture drop for `begin_load`/`start_live`. For the decode-failure arm, gate the clear on `!self.history.is_empty()` — `LoadUpdate::Failed` carries no `FrameOrigin` (load_service.rs:41-45), and `begin_load` clears history first (app.rs:353), so the gate is semantically exact.

### 2.2 One failed or unavailable render freezes playback forever at a 60 Hz spin — and a failing render hot-loops the render worker indefinitely
**high · S · mobile-relevant · files:** `app.rs:721` / `app.rs:659`

`advance_playback` (app.rs:717-724) returns after `request_repaint_after(16ms)` unless `visible_panes_ready` (app.rs:1868-1877), which requires **every** visible pane to hold a current-stamp texture. The unavailable arm of `ensure_render_requested` (app.rs:1287-1293) and `RenderUpdate::Failed` (app.rs:652-663) both leave `pending_stamp=None` and `texture=None` — playback halts on that frame forever while repainting at ~60 Hz. Worse: nothing records that a stamp failed, so on the next frame `ensure_render_requested` resubmits the **identical** request (preconditions at app.rs:1295-1301 all pass), the worker fails it again and its own `request_repaint` (render_service.rs:122) sustains the cycle — even with playback paused. Persistent failures are reachable on real data: `SamplerError::NoReflectivityCuts` for a velocity-only file or a live volume caught before its first surveillance sweep (sampling.rs:79-82); whole-field rejection on any NaN cell ("any nonzero count rejects the field", stats.rs:86-88); "implausible field" from render_service.rs:279-288; `resolve_cut_index` returning None for a moment absent from a legacy archive (app.rs:1681-1712). Each derived retry costs a measured 15–20 ms on the single worker, queuing every other pane behind it.

**Fix:** a terminal per-pane state (`Rendered | Unavailable | Failed{stamp}`) on `PaneRuntime`. `visible_panes_ready` treats Unavailable/Failed as ready; `ensure_render_requested` never resubmits a stamp recorded as Failed — any clock bump (new chunk, camera, product, palette) naturally retries. One mechanism fixes the freeze and the hot loop.

### 2.3 Every render completed during a camera gesture is discarded; the pane shows drag-start pixels for the entire gesture
**high · S · mobile-relevant · file:** `app.rs:668`

`install_render` (app.rs:667-668) early-returns unless `rendered.stamp == current_stamp` exactly; `RenderStamp` includes the per-pane view generation (generation.rs:60-75); every pointer-move frame bumps the view clock via `camera_changed → apply_camera_from → invalidate_view_panes` (app.rs:1181-1184). The single serialized worker (render_service.rs:107-127, newest-wins lane) completes ~25 full renders/s at default Smooth quality (measured 39.7 ms p50 @2560×1440 on real KDMX; Native 9.5 ms) — every one stale-by-view on arrival during continuous motion, so **100% of gesture-time render CPU is discarded** and no fresh pixels land until the pointer pauses. The discard is provably unnecessary: `paint_transformed_texture` (pane_canvas.rs:824-849) reprojects the installed texture through `texture.camera`/`texture.viewport`, so a view-stale render draws geometrically correctly.

**Fix:** accept a completed render whose stamp differs only in the view generation (still reject session/frame/pane/palette/sweep mismatches); it installs with `rendered.camera` and the existing reprojection draws it correctly, while `ensure_render_requested` still re-requests the exact-stamp render. `visible_panes_ready` (app.rs:1875) keeps exact-equality semantics for playback gating. **Coordinate with the view-stability workflow before starting.**

### 2.4 Derived products recompute the full 848,241-cell volume field on every camera tick — and at sweep-reveal cadence on live panes
**high · M · mobile-relevant · file:** `render_service.rs:266` (doc admitting it at 247-250)

`render_derived` calls `compute_volume_field` per request (compute path at render2d/src/derived/compute.rs:46-80; grid sized at compute.rs:7-10, `INTERACTIVE_SPACING_KM=1.0`). Independently measured **twice** on the real KDMX volume (two separate harnesses): 15.3–20.1 ms and 19.7–23.3 ms p50 across all seven products (CREF/ET18/VIL/VILD/MESH/POH/POSH), 32 threads, cell count confirmed exactly (921² = 848,241). Every camera change of a derived pane pays this plus the field raster on the single worker; a 4-pane linked pan serializes to ~80–115 ms per view step. On the live edge it is worse: `advance_sweeps` (app.rs:1369+) steps the reveal for derived panes too, `sweep_clock` is in the stamp (app.rs:1491-1501), and the cadence self-paces to render turnaround — **~25–40 identical recomputes per second for the entire arrival of every lowest tilt.** On ~6-core mobile hardware this is several-fold worse and a straight battery drain.

**Fix:** memoize the `ScalarField2D` in the render worker with a small byte-bounded LRU. Key correction from verification: `Arc::as_ptr` alone is ABA-unsafe (freed volume addresses recycle) and `HailEnvironment` has no revision field — key on (volume_time, site, cuts+radial extent, derived id, environment **value**, spacing); `HailEnvironment` derives `PartialEq` (product_engine/src/environment.rs:83) so the value-key works. Pans and sweep steps become pure lookups; the code's own comment already names this cache as next work.

### 2.5 Vrot silently measures across volumes, products, and sites — wrong numbers in a warning-criteria workflow
**high · S · file:** `vrot.rs:322`

`VrotState::mark_stale` and all four `StaleReason`s have **zero callers** (workspace-wide grep). `app.rs` touches `vrot_state` only on toggle-off (965), Clear (971), and pane change inside `take_vrot_sample` (1580-84); `install_loaded_volume`, `commit_history_selection`, playback advance, product change, `begin_load`, and `start_live` all leave it alone. `VrotSample` (vrot.rs:72-86) carries no volume identity, so a new volume installing between clicks (live feed at ~1.2 s cadence, timeline step, playback) pairs gates from two volumes and reports "Vrot NN kt" as valid — in a workflow citing Thompson et al. 2017 warning criteria. A product change between clicks pairs a DVEL gate with an SRV gate, **silently mixing ground-relative and storm-relative frames**. A site switch keeps the pending endpoint (old-anchor coordinates) alive into the new radar's data, and a Complete measurement stays displayed un-badged forever (app.rs:974). One honest exception: cross-**tilt** is refused — `measure()` rejects differing cut indices (vrot.rs:359-361, `DifferentCuts`).

**Fix:** wire `mark_stale` at every frame-change site: `install_loaded_volume` on signature change, `commit_history_selection`, and the playback advance → `NewVolume` (all three already compute before/after signatures next to `frame_clock.bump()`); product change on the vrot pane → `DifferentProduct`; `start_live`/`begin_load` → `DifferentSite` (that is the variant's actual name) or clear + `vrot_pane=None`. `change_active_tilt` wiring is optional belt-and-braces.

### 2.6 Persistence is a lie: `AppSettings` has zero readers; every user choice dies with the process
**high · M · mobile-relevant · file:** `crates/settings/src/lib.rs:6`

The settings crate is a dependency of no other crate (grep of every Cargo.toml); `AppSettings`/`settings::` appear nowhere outside it. eframe 0.34.3 is pulled with default features — the `persistence` feature is off (no ron/persistence deps in Cargo.lock), there is no `fn save` on the `impl eframe::App` (app.rs:1880), and main.rs passes default `NativeOptions` — so not even window geometry or egui memory survives exit. `WorkstationApp::new` (app.rs:181-256) hardcodes every field: layout, quality, color tables, basemap/provider, warnings, empty site. `AppSettings` itself models almost none of the real state. On iOS/Android the OS kills the process routinely, so the app forgets everything between foregroundings.

**Fix:** extend `AppSettings` to a workspace snapshot {layout, per-pane product id + tilt + links, quality preset, per-family table name, style preset id, tile provider, show_warnings, last site, vol3d prefs, window geometry}; load in `WorkstationApp::new` from the existing LOCALAPPDATA/FahrenheitResearch/RadarWorkstation convention (live_service.rs:193-199); save debounced plus via `eframe::App::save`. Resolve saved product ids through `try_from_product_id` (product.rs:116) with a visible "unknown product" status — its doc already demands exactly that.

### 2.7 3D pane zoom reads only `smooth_scroll_delta`: pinch dead on every touch device, and Ctrl+scroll / macOS trackpad pinch dead on desktop today
**high · S (share the gesture reader) + M (full touch orbit) · mobile-relevant · files:** `vol3d/pane.rs:1091`, `vol3d/camera.rs:433`

pane.rs:1090-1095 is the 3D pane's only zoom input (`smooth_scroll_delta.y`, gated on `response.hovered()`); the (currently dead, §2.8) orbit dolly in camera.rs:433/449-461 reads the same field. Grep across all of vol3d: **zero** occurrences of `multi_touch`, `zoom_delta`, or `Event::Zoom`. On iOS/Android pinch arrives only through those channels, so the flagship 3D explorer rotates but is pinned at its initial distance forever (default mode Orbit, vol3d.rs:329; no distance slider — pane.rs:926-930 exposes only fov/exaggeration; Fly moves exclusively via WASD/QE, camera.rs:671). Verification upgraded this to desktop-visible **today**: egui zeroes `smooth_scroll_delta` when the zoom modifier is down and reports trackpad pinch as `Event::Zoom` — `pane_canvas.rs:313-321`'s own doc comment records this exact failure as "why Ctrl+scroll used to do nothing at all in this pane." The complete reading already exists one module away in `pane_canvas::wheel_zoom_factor` (309-364): raw MouseWheel by unit, `Event::Zoom`, `multi_touch().zoom_delta` with the double-count trap handled. The recurring each-half-correct seam, verbatim.

**Fix:** extract the pinch/zoom-event half of pane_canvas's reader (~15 lines) into a shared `pub(crate)` helper returning a zoom factor; multiply it into the 3D dist update (and into `camera::drive_camera` when §2.8 lands). Do **not** lift `wheel_zoom_factor` wholesale — its notch-burst state is keyed per 2D `PaneId`. Map two-finger `translation_delta` to truck/pan in Orbit; hide Fly (or give it on-screen dolly) when `InputState::any_touches`. Verify with Ctrl+scroll on desktop over a real cached volume plus the iPhone build.

### 2.8 The 1,999-line two-camera module is fully dead: Fly mode unreachable, and the live orbit zoom keeps the dead-notch defect camera.rs already fixes
**high · M · file:** `vol3d/camera.rs:37`

camera.rs (1,999 lines, 34 tests) carries `#![allow(dead_code)]` at line 37 whose comment promises deletion "in the commit that pastes them into vol3d/pane.rs" — which never happened. Zero call sites for `drive_camera`/`camera_controls`/`set_camera_mode`/`FlyInput` outside camera.rs; `enter_fly_mode` is called only from a vol3d.rs unit test (vol3d.rs:1873) and annotations.rs's Fly construction is inside `cfg(test)` (mod at line 826). So `camera_mode` is Orbit forever, making the Fly branch of `camera_basis` (vol3d.rs:449) and the `fly_x/y/z` plumbing (pane.rs:1138-1140) dead freight, shipped silently under vol3d.rs:24's module-wide `allow(dead_code)`. Meanwhile the live zoom (pane.rs:1091-1093) clamps `dist` to [0.35, 6.0] but the renderer floors at `orbit_distance() = dist.max(zspan()*0.45+1.25)` (vol3d.rs:413) — at the default 30 km box (BOX_HALF_KM=30 box_frame.rs:108, BOX_TOP_M=18000, exaggeration 1.5) the floor is **1.655**, so **~15 wheel notches move nothing** and must be spent again zooming out. This is exactly the defect `orbit_radius_floor` (camera.rs:344, clamp at 331) documents and fixes in code nobody runs; the fly camera — per the module doc, "the reason a second one was asked for" — is unreachable.

**Fix:** wire the integration the header promises: replace pane.rs's inline drag/scroll handler with `camera::drive_camera(FlyInput{..})` (fixes the dead-notch zoom), surface `camera::camera_controls` in the 3D toolbar so Fly is reachable, then delete the inline handler, camera.rs:37's allow, and narrow vol3d.rs:24's module-wide allow so future unreachable camera code fails clippy. Verify on a real cached volume: wheel hits the floor with no dead notches; the Fly toggle puts the eye inside an echo.

### 2.9 Live Level II disk cache grows without bound — 1.07 GB in ~2 days here; 17.5 GB proven endpoint on this box
**high · M · mobile-relevant · file:** `crates/data_source/src/lib.rs:666`

`download_realtime_volume` writes full assembled volumes plus a persistent `.chunks/<site_time_id>/` per volume (lib.rs:666-672) and nothing ever deletes either: the only `remove_file` calls in data_source (756, 764, 1253, 1261) are atomic-rename housekeeping, and live_service/workstation_app contain zero prune/evict/sweep code. Measured now on real data: level2-live totals **1,072 MB** — 66 complete volumes plus 540 MB of retained `.chunks` — spanning 2026-08-17 00:22 → 2026-08-18 20:44 (~0.5 GB/day at single-site dev usage; multi-site scales it). The endpoint is measured, not extrapolated: **BowEcho's identical cache pattern on this machine is 17,506 MB.** The contrast is in-repo: the tile cache is bounded (`TileCacheConfig::max_disk_bytes` 512 MiB, store.rs:80, byte-counted sweep at basemap_tiles/src/cache.rs:45). On a 64/128 GB phone this reaches Settings→Storage complaints within weeks.

**Fix:** apply the TileDiskCache pattern (bytes counter + sweep interval + prune-to-fraction) to the live cache — mobile default ~256 MB, desktop 2–4 GB — and delete a volume's `.chunks` dir once the complete file is assembled and renamed (lib.rs:765 is the exact point).

## 3. Mobile release blockers

Everything verified `mobile:true`, as the working checklist toward the iOS/Android plan (native egui inside a SwiftUI/JNI shell — the pattern proven with BowEcho on iPhone 16 Pro; see bowecho `docs/ios-port-notes.md`). Items detailed elsewhere are pointers; mobile-only items carry their detail here.

### A. Touch input — the app does not function without these

- [ ] **Site taps dead on touch** — `pane_canvas.rs:647` hit-tests clicks with `hover_pos()`, which egui-winit clears on the touch-release frame (Released + PointerGone pushed in one batch on `TouchPhase::Ended`, egui-winit 0.34.3 lib.rs:910-919; `latest_pos` cleared at input_state/mod.rs:1208-1212 while `interact_pos` survives for the click frame). Decisive: the Ctrl+click path in the **same function** already uses `response.interact_pointer_pos()` (pane_canvas.rs:256) and would survive. Switch the marker hit-test to `interact_pointer_pos`; keep `hover_pos` for highlight only. Add a Touch Start/End + PointerGone replay test. *(high, S)*
- [ ] **No touch path to nearest-S-band selection** — `nearest_site.rs:243-245`/266-272 requires Ctrl/Cmd+click; no Ctrl exists on glass, and combined with the marker bug a phone user has **no** pointer-based radar selection at all. Route `response.long_touched()` in as a second gesture using `interact_pointer_pos` (the pane is `Sense::click_and_drag`, pane_canvas.rs:165; egui synthesizes long-press, response.rs:204-214). Sharpened in verification: egui long-press **also** raises `clicked()` in the same frame (interaction.rs:143-155), so the long-press branch must out-precedence the Vrot-sample and plain-click branches at app.rs:1150-1177, not just the marker path. Only existing `context_menu` is vol3d/pane.rs:1096. *(high, S)*
- [ ] **3D pinch zoom** → **§2.7**. *(high)*
- [ ] **Pinch anchors and pans on finger 1, not the gesture centroid** — pan via `pointer.delta()` (pane_canvas.rs:175-181), anchor via `hover_pos()` (183-195) — both finger-1 quantities, since egui-winit synthesizes pointer events only from the first touch — while the zoom **factor** correctly comes from `multi_touch().zoom_delta` (361-365). `MultiTouchInfo::center_pos`/`translation_delta` (egui touch_state.rs:19,55) sit unread. When `multi_touch()` is Some: anchor on `center_pos`, pan by `translation_delta`, skip the pointer-delta pan that frame. Testable on a Windows touchscreen before the Mac session. *(medium, S)*
- [ ] **Drag-pan and wheel-zoom never activate the pane they act on** — `set_active` is called only in the three click branches (app.rs:1152-1177); in egui 0.34.3 a movement past click tolerance is a drag, never a click, and wheel keys off `hovered()` (pane_canvas.rs:183-196). Keyboard flight, `change_active_tilt` (app.rs:1733), the toolbar (app.rs:742), and the 3D product-follow (app.rs:1036) all read the active pane — so panning pane 2 onto a storm then pressing +Tilt changes pane 1. On touch, drag is the *primary* gesture: the active pane would essentially never follow the pane in use. Report an interacted flag from `draw_pane` (drag_started or zoom factor ≠ 1.0) and `set_active` on it. *(medium, S)*
- [ ] **Double-tap resets the camera mid-Vrot-measurement** — pane_canvas.rs:209-212 resets on `double_clicked()` unconditionally; the second release is simultaneously the second Vrot sample (using pre-reset previous-frame `hovered_world_km` → a near-zero-baseline pair) **and** a `Camera2D::default()` reset propagated to every camera-linked pane. The codebase documents this exact egui coupling itself (nearest_site.rs:253-266) and defends the nearest-site path with `!double_clicked` — the Vrot path has no such defence. Gate the reset on `!vrot_active`. *(low, S)*
- [ ] **Hover-gated information layer has no touch story; the warnings chip toggles the layer off when tapped for detail** — probe and range/az/lat-lon readout require hover (pane_canvas.rs:944-961, 975-1000); site labels draw only on hover when >40 on screen (:709) so a national touch view is anonymous squares; warnings detail lives in `on_hover_text` while `clicked()` toggles the layer (app.rs:794-804) — the tap a phone user makes to *read* a tornado-warning list turns warnings **off**; Vrot instructions hover-only (app.rs:957-962); 16 `on_hover_text` sites total. Touch pass: tap-to-pin probe, long-press chip opens detail without toggling, Vrot hints in the status line, always label the nearest-N sites. *(medium, M)*

### B. Platform substrate — the app is dead on arrival without these

- [ ] **Per-OS cache roots** — three independent path constructions, none injectable: `default_live_cache_dir` (live_service.rs:193-214) falls to `std::env::temp_dir()` on Android = `/data/local/tmp`, which an app cannot write → **every live download errors, live feed dead**; on iOS it lands in `$HOME/.cache` — outside Library/Caches, never OS-purgeable, included in iCloud backup. `sites_service::cache_path` (sites_service.rs:83-92) returns None on iOS/macOS/Android → cold offline start has zero site markers. Basemap `default_cache_dir` (store.rs:112-122) has no iOS arm. Hard call sites: app.rs:231, scene.rs:125 → tiles.rs:345. Add `settings::app_cache_root()` with cfg arms (iOS: `$HOME/Library/Caches`; Android: set-once OnceLock the shell fills before eframe starts) per BowEcho's notes line 41. *(high, M)*
- [ ] **Cache eviction** → **§2.9**. *(high)*
- [ ] **Mobile memory-budget profile** — defaults sum past jetsam: history 1 GiB / 30 frames (history.rs:9-10, used unmodified at app.rs:195; measured 74.3 MiB per real KTLX VCP-212 volume → cap fills at ~13 frames, ~1 GiB steady state), tile GPU 160 MiB (tile_gpu.rs:124), map-geometry CPU residency 192 MiB (residency.rs:13), transient supersample rasters up to 64 MiB per pane (quality.rs:68), plus vol3d and pane textures ≈ **1.5–1.7 GiB working set** before wgpu/OS overhead, against 2–3 GB jetsam on non-Pro hardware (4.4 GB ceiling even on iPhone 16 Pro per BowEcho). Every knob already has a setter (history.rs:250 `set_policy`, tile_gpu.rs:131 `with_budget`, store.rs:80 `max_disk_bytes`) — a `BudgetProfile` (desktop/mobile) is pure wiring. *(high, S)*
- [ ] **Persistence** → **§2.6** — mobile OSes kill the process routinely; today the app forgets everything between foregroundings. *(high)*
- [ ] **Bytes-based archive ingress** — `begin_load` takes `PathBuf` only (app.rs:341), the flow is a 260 pt absolute-path TextEdit (app.rs:761-766) or OS drag-drop that ignores `DroppedFile.bytes` (app.rs:710-715); neither exists on iOS (document picker, security-scoped URLs) or Android (SAF). Genuinely small: load_service already goes to bytes immediately (fs::read at load_service.rs:97; `decode_*_from_bytes` at 162-169) — add `begin_load_from_bytes`, honour `DroppedFile.bytes`, hide the TextEdit when a shell file-open hook is registered. *(low, M)*
- [ ] **Cancellable session download** — `poll_session` calls `download_realtime_volume` (live_service.rs:294), defined as the cancellable variant with a constant-false closure (data_source/src/lib.rs:604-609); commands drain only between polls (live_service.rs:229-248). Site switch or Stop stalls behind a 3.5–18.6 MB download — seconds on broadband, much longer on cellular. The cancel machinery already exists in the same file: mirror `backfill_cancel` (live_service.rs:66, 98, 445-448). *(low, S)*

### C. Layout and touch ergonomics

- [ ] **Toolbar wraps to ~6 rows on a 393 pt phone** — one `horizontal_wrapped` (app.rs:757) carries ~24 widgets; explicit widths alone sum to 1,040 pt (260 path TextEdit app.rs:762 + 56 site + 112 layout + 210 palette app.rs:893 + 140 basemap app_support.rs:35 + 170 imagery app_support.rs:72 + 92 quality), the full run ~2,000–2,300 pt; the layout has never rendered below `min_inner_size` 960×620 (main.rs:143). Priority groups with an overflow menu below ~700 pt — width-driven, so narrow desktop windows benefit too. *(medium, M)*
- [ ] **Product picker clipped at phone width** — `PICKER_WIDTH = 468.0` (product_picker.rs:39) forced via `set_width` (:356) inside a plain `egui::Area` (app.rs:838-841), which — unlike a Window — has no Resize container and cannot shrink content; at 393 pt the right ~75 pt, including the right-aligned 150 pt palette swatches (:808-809), is unreachable. ### D. Performance and battery on phone cores

- [ ] **Derived-field cache** → **§2.4**. *(high)*
- [ ] **Accept view-stale renders** → **§2.3**. *(high)*
- [ ] **Moment-cache reuse** → **§4.2**. *(medium, S)*
- [ ] **Color32 conversion off the UI thread** → **§4.3**. *(medium, S)*
- [ ] **Incremental live decode** — every chunk arrival re-reads and fully re-decodes the growing volume from byte zero (`VolumeFingerprint` includes chunk_count/total_size, live_service.rs:29-48; `process_request` does `fs::read` + full decode, load_service.rs:97-110). Real volumes carry 15–91 chunks (KDMX: 91); full decode measured 69–77 ms → ≈3 s of pool time plus ~1 GB cumulative re-reads per 6-minute volume, redoing bzip2 blocks already decoded. Keep decompressed blocks/parsed cuts for the current volume and decode only appended chunks (boundary is known — chunks are cached individually). *(medium, **L** — schedule for the mobile beta window, not the next desktop release)*
- [ ] **LINEAR texture filtering** — `TextureOptions::NEAREST` at both install sites (app.rs:678 in-place, app.rs:695 fresh); between camera change and next render the old texture is stretched with hard pixel blocks — and on touch, pinch-zoom lives in that interim continuously. At the settled state the draw is exactly 1:1, so LINEAR is visually identical there and strictly smoother during the stretch. One line. *(medium, S)*
- [ ] **Clamp render quality during gestures** — every camera tick submits at `self.quality` unconditionally (app.rs:1344); measured Native 1.6 / Smooth 8.3 / High 17.0 / Ultra 29.2 ms at 900 px, so continuous Ultra zoom updates at ~25-30 Hz single-pane and 7–9 Hz four-pane (serialized, ~110 ms+ on the last pane). Clamp in-gesture requests to Smooth and schedule one final render at the chosen preset on settle — the per-request quality field exists for exactly this (render_service.rs:45-47). *(medium, M)*
- [ ] **Cap the raster at a physical-pixel budget** — `radar_raster_view` (view.rs:281-301) sizes at points × pixels_per_point squared; measured **5.2 ms Native at exactly iPhone 16 Pro resolution (1290×2796) on a 32-thread desktop** — Ultra extrapolates to ~130 ms/frame before the phone's narrower core count — plus a full-frame convert + ~14 MB re-upload per install (app_support.rs:173-181, app.rs:668-696) at sweep cadence. Cap Mpx per quality tier, let the GPU upscale with LINEAR (pairs with the filtering fix), reuse a persistent pixel buffer. *(medium, M)*

## 4. Fast follows

Medium items worth batching, ordered by value.

1. **Quality invalidation is wrong in both directions** *(S)* — merged from two dimensions. Under-invalidation: `RenderStamp` has no quality field (generation.rs:60-75) and a quality change bumps only *visible* panes (app.rs:981-985; `set_layout` bumps nothing, workspace.rs@2101a0d:173-178; viewport bump needs a ≥0.5 pt rect change, app_support.rs:167-169) — Four→One→change quality→Four returns panes 1–3 at the old quality, deterministically on archive/paused sessions (live self-heals via the ~1.2 s frame bump). Over-invalidation: `render_derived` never reads `request.quality` (render_service.rs:251-310), so every quality toggle recomputes derived fields (19.7–23.3 ms measured) for a bit-identical picture. Fix both at once: give quality its own `GenerationClock` inside the stamp (exactly as palette already has, app.rs:864/899 — which is why hidden panes are covered for palette but not quality), and skip derived panes on quality-only changes.
2. **Moment cache rebuilt every render request** *(S)* — `render_request` constructs and drops `ViewportMomentCache` per request (render_service.rs:180-194); inputs contain no camera. Measured: 7.1–10.1 ms build per re-render (18% of a Smooth re-render @1440p); the DVEL variant re-runs dealiasing every request (3.0–3.3 ms). One-entry-per-pane worker-local cache keyed on (volume ptr + identity, cut_index, source moment + dealiased flag, quality, tables ptr).
3. **Full-frame RGBA→Color32 conversion on the UI thread per install** *(S)* — `color_image_from_rgba` (app_support.rs:173-180) maps every pixel and collects a second full-frame Vec inside the update pass (call site app.rs:671): measured 3.85 ms @2560×1440, 6.43 ms @4K (ecolor's a=0/a=255 fast paths accounted for), recurring at sweep-reveal and playback cadence across 4 panes. Move the conversion onto the render worker (`RenderedPane` carries an `egui::ColorImage`); better, emit premultiplied RGBA from render2d so it becomes a cast (M).
4. **Supersample budget silently collapses the quality ladder while the UI promises 16×** *(S label / M real fix)* — `effective_supersample_factor` (quality.rs:85-103, budget at :68) clamps High (3×) and Ultra (4×) to Smooth's 2× at 2560×1440 and **all presets to 1× at 4K**. Demonstrated empirically: real ladder at 900 px (8.9/16.0/29.1 ms) vs flat at 1440p (39.7/36.3/32.7 ms) vs 4K Smooth 13.9 ms ≈ Native 12.4 ms with zero partial-alpha pixels — the box filter provably never ran. The tooltip promises "sixteen times" (app.rs:924-927) and quality.rs's own doc says callers should display the effective factor. Minimum: show it ("Ultra (2× here)"); real fix: viewport-scaled budget or tiled supersampling. Note: only the supersample rungs collapse — the soften flag still differs.
5. **Backfill and live decodes can evict each other on the single newest-wins load lane — and the loss is permanent** *(S)* — one lane (load_service.rs:11), same-lane replace in jobs.rs; both live updates and `run_backfill`'s publish (live_service.rs:403+) arrive on the same channel with the same shape (app.rs:485-537). The eviction window is narrow (same-frame drain of two VolumeReady updates, ~16–50 ms per session's one backfill publish; wider on slow mobile hardware) but both consequences are permanent: `last_fingerprint` is set on *send* (live_service.rs:318) so an evicted final-chunk decode is never republished — permanent PARTIAL badge (app.rs:1096) — and `backfill_started` is never cleared ("one session gets one attempt", live_service.rs:57-61) so an evicted backfill silently undoes commit ddc30d8's feature for the session. Fix: `backfill` flag on `VolumeReady`, a lane parameter (LANE_LIVE/LANE_BACKFILL), route in `poll_live_results`. Newest-wins within the live lane stays correct because the file grows in place.
6. **Site-marker hit-test does not stand down while Vrot is armed** *(S)* — `clicked` is defined as `response.clicked() && clicked_site.is_none() && ctrl_clicked.is_none()` (pane_canvas.rs:295-297) and the marker gate checks modifiers only (`site_marker_click_allowed`, nearest_site.rs:297), so a click inside the 9 pt halo (pane_canvas.rs:78-80) mid-measurement skips the Vrot branch and runs `start_live` — session bump, history cleared, all panes cleared. Near-radar couplets sit within 9 pt of the marker at working zooms, and start_live never clears vrot_state (§2.5), so the surviving endpoint pairs against the **new** radar. Gate the hit-test on `&& !vrot_active` — the one-rule-in-the-predicate convention the file itself documents (nearest_site.rs:276).
7. **Map-continuity batch** — three related seams, best landed together:
   - *Style change blanks the vector map while chrome flips instantly* (M) — `set_style` (scene.rs:180-190) clears geometry/pending; `geometry_for_pane` (scene.rs:246-259) has no stale fallback; `paint_map` draws nothing on None (pane_canvas.rs:739-741) while chrome is read fresh per frame (app.rs:1083-1087). Keep the old style's geometry **and its chrome together** until the new geometry installs, then swap atomically — stale-geometry-under-new-chrome can be illegible (dark lines on dark). Residency is a plain byte-budgeted LRU (residency.rs:44-118), so keep-stale is free.
   - *First zoom across an LOD boundary vanishes the whole map* (S) — `key_for_pane` swaps the `LodBucket` (scene.rs:192-211; hysteresis view.rs:336-373) and the unbuilt bucket draws nothing while the previous bucket is still resident (evicted only by budget, scene.rs:424-439). Draw the nearest resident bucket for the same dataset+projection+style while the requested one builds — the tile layer already solves the identical problem with `ancestor_substitutions` (tiles.rs:634-638).
   - *Site switch: radar drops, long pause on wrong geography, then the map blanks and rebuilds* (M) — `start_live` (app.rs:368-390) clears immediately but the anchor moves only at first decode (install_loaded_volume app.rs:580-593 → `set_radar_anchor` scene.rs:166-178, which clears the map again), though the catalog holds every site's lat/lon at click time (`LocatedSite`; click paths app.rs:1152-1176). 8. **Live sweep quality pop** *(M)* — `render_blended_sweep` (render_service.rs:319-402) deliberately renders the *entire pane* (arriving wedge plus previous sweep underneath) with no quality passes, then the closing frame snaps to the chosen preset — Native vs Smooth measured at 41,015 vs 118,968 colour-boundary pixels on real KDMX, visibly different full-frame, twice per tilt cycle forever on a live pane.
